# Paired agent sessions: Click on vs off (2026-09-12)

Eight headless Claude Code sessions with Opus 5 performed the same bug-fixing
task on fresh copies of the same fixture: four with the Click plugin disabled
(arm A) and four with it enabled (arm B), alternated A B B A A B B A and run
one at a time. This is a measured record of complete agent tasks on a fixture,
not a production measurement: the fixture is small, its four shards are equal
in length, and one machine and one model were used.

| median (min–max) | A: Click off | B: Click on | change |
|---|---|---|---|
| session wall time | 381 s (364–408) | **123 s (120–128)** | **−68%** |
| test wall time inside the session | 265 s (261–274) | 58 s (56–60) | −78% |
| test module executions | 20 (5 full runs × 4) | **10** (4+3+2+1+0) | **−50%** |
| turns | 16 (10–19) | 16 (16–19) | 0 |
| cost | $0.60 (0.48–0.75) | $0.66 (0.55–0.69) | **+11%** (mean +5.6%) |
| output tokens | 3,038 | 3,847 | +27% |
| total tokens incl. cache | 497k (454k–727k) | 681k (476k–744k) | +37% (mean +19%) |

All eight sessions fixed all three seeded bugs, left `tests/` untouched, and
passed an independent full-suite run afterwards. Every Click-on session sent
all five test cycles through `click-gate verify` (20/20 requests). The time
saving did not come with a token saving: Click-on sessions cost more, and the
record says so on the same line wherever it is cited.

`evidence/analysis.txt` is generated by `evidence/analyze.py` from the raw
per-session data and is the authoritative table.

## Setup

- **Click** v1.0.0, installed plugin `click@click` at commit `b621c00`
  (`dist/claude`), Evidence mode, no repository policy, no committed shard plan.
- **Host** Claude Code CLI 2.1.269, `claude -p --output-format stream-json`,
  `--model claude-opus-5`, `--max-turns 80`, tools `Bash Read Edit MultiEdit
  Write Glob Grep`, timeout 2400 s. Arm A passed
  `--settings '{"enabledPlugins":{"click@click":false}}'`. Both arms also
  disabled the unrelated `deploy-on-aws@agent-plugins-for-aws` plugin installed
  on this machine (see finding 1).
- **Machine** Ubuntu 24.04.4, kernel 7.0.0-31, Intel Core Ultra 5 225H
  (14 CPUs), CPython 3.12.3, strace 6.8. Another interactive session was
  running its own test suites on the machine during the measurement; the load
  average at each session start is in `summary.json`.
- **Fixture** (`evidence/make_fixture.py`): a `ledger` package with four modules
  and four `unittest` files, each carrying a few functional tests plus one
  CPU-bound test (chained PBKDF2, 100 records × 300,000 rounds, no sleep). A
  full `python3 -m unittest discover -s tests` run took 41–57 s on the loaded
  machine (about 40 s idle). Three bugs are seeded — `alpha.paginate` starts
  the first page at `page * size`, `beta.allocate` drops the leftover cents,
  `gamma.slugify` does not collapse repeated separators — so 13 of 19 tests
  fail initially and `delta` passes from the start. Each session got a fresh
  copy in its own Git repository, so no receipts carried across sessions.
- **Task prompt** (identical in both arms):

  > The test suite in this repository fails. Run the full suite with
  > `python3 -m unittest discover -s tests` to see the failures, then fix the
  > bugs in the `ledger` package one module at a time. Rules: do not modify
  > anything under `tests/`; after fixing each module, run the full test suite
  > again to confirm the fix; when every test passes, run the full suite one
  > final time and stop. Work only inside this repository. Finish with a short
  > list of the files you changed.

- **Metrics** are derived from the transcripts (`evidence/session-*/`):
  session wall time and token usage from the `claude -p` result event; test
  executions and test time from the Bash tool outputs — in arm A each
  `Ran 19 tests in Xs` is one full run of four modules, in arm B each
  `[Click verification i/n:...]` line is one executed shard child and Click's
  `[Click 결과]` line gives the parallel wall clock. The final
  suite check and `git status` were run by the harness after each session.

## Per-request trajectory

Arm A ran the whole suite five times per session. Arm B was sharded
automatically into four file children on the first request and then executed
only the children whose inputs had changed or had failed last time:

```
A: 4/45s  4/57s  4/51s  4/57s  4/53s        (executed modules / test wall)
B: 4/14s  3/16s  2/14s  1/15s  0/0s*        (* every shard reused)
```

The trajectory was identical in all four Click-on sessions. Click's own
result lines for the last two requests of one session:

```
[Click 결과] 4개 중 1개 실행 · 3개는 마지막 통과 이후 입력 불변으로 현재 유효(재사용) · 약 45.61초 재실행 생략〔추정〕; ...
Click reused 4 current unchanged-tree verification receipts
```

## What the numbers do and do not show

- The **wall-time gain is mostly concurrent shard execution**, not reuse: the
  four shards are equal in length, so any request that executes at least one
  shard takes about 15 s. Reuse shows up as executions (20 → 10) and as the
  final request, which executed nothing. A suite with one dominant shard would
  attribute more of the wall time to reuse; this fixture cannot show that.
- **Tokens went up, not down.** The difference is almost entirely cache-read
  input (+104k mean) from about 1.6 extra turns per session, plus the
  ~200-character `click-gate verify '{...}'` command the agent typed each time
  (+674 output tokens). Click's tool output was not larger than unittest's
  (6.8k characters per Click-on session versus 6.8k–13.7k for unittest).
  Cache reads are the cheapest token class, so the cost difference is +$0.03
  mean (+5.6%), +11% by median. This fixture's test output is short, so the
  "output the host did not read again" saving had nothing to save.
- 4 versus 4 sessions on one machine, one model, one task. The two arms do
  not overlap on any time metric, but this is not a statistical claim about
  other projects.

## Findings from the pilot that are product facts

1. **Another installed plugin breaks Click reuse on Claude Code.** Claude Code
   appends every installed plugin's `bin` directory to the Bash tool's `PATH`
   (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/bin`). Click's
   environment fingerprint drops its own directory but not the others, so with
   `deploy-on-aws@agent-plugins-for-aws` installed the Hook-side and runner-side
   fingerprints differed on every request (`[Click] Verification runner
   environment changed after preparation; rebound to the current canonical
   environment.`), no receipt ever matched, and the second identical request
   re-ran the suite. Disabling that plugin in both arms removed the message and
   the second identical request was reused. Fix: treat every plugin `bin`
   directory under the plugin cache root as host-owned, as Click's own already is.
2. **Haiku 4.5 ignored the Evidence directive; Opus 5 followed it.** With the
   identical prompt and the directive verbatim in its context
   (`UserPromptSubmit hook additional context: Click Evidence mode is
   enabled. Run every test or check command through Click ...`), the Haiku
   pilot (`evidence/pilot-haiku/`) ran `python3 -m unittest discover -s tests`
   directly in all four cycles and issued no `click-gate` request; Opus 5
   issued one for every cycle in all four sessions (20/20).
3. **The instrumentation was rejected for the right reasons.** The first
   fixture recorded each module run from `tests/_workload.py` with
   `time.time()`, `os.environ.get(...)` and an append to a file outside the
   repository. The native observer reported `time-random-input` for the clock
   call, so an identical rerun was not reused; the split analysis reported
   `split-independence-needs-review` (`file-write-or-unknown-mode`,
   `process-environment-introspection`; unknown dependencies
   `environment-access`, `unresolved-file-access`), so no automatic shard plan
   was generated and the parent ran as one shard. Removing the instrumentation
   restored both. The metrics above therefore come from the transcripts, and
   the fixture in `evidence/make_fixture.py` is the instrumentation-free one.

## Reproduction

```sh
python3 docs/history/agent-ab-2026-09-12/evidence/run_ab.py --root /tmp/click-ab --model claude-opus-5 --order ABBAABBA
python3 docs/history/agent-ab-2026-09-12/evidence/analyze.py /tmp/click-ab
```

`run_ab.py` creates a fresh fixture per session with `make_fixture.py`, runs
`claude -p` with the settings above, and writes `summary.json`, per-session
`bash_calls.json`, `result.json` and the full `stream.jsonl`. It disables the
`deploy-on-aws` plugin in both arms because it was installed on the
measurement machine; on a machine without other plugins that entry is inert.

## Addendum: the plain `click-gate verify -- <argv>` form (v1.1 candidate)

The JSON envelope the model typed for every cycle was the main output-token
overhead above, so the v1.1 candidate accepts `click-gate verify -- <check
argv>` and the Evidence directive shows that form. Two more Click-on sessions
(`evidence/argv-form/`) ran the same task with that build loaded from a pinned
copy outside the worktree via `--plugin-dir` (installed Click disabled). Both
used the plain form for all five cycles.

| median | JSON form, Click on (n=4) | plain form, Click on (n=2) | Click off (n=4) |
|---|---|---|---|
| output tokens | 3,847 | **3,219** | 3,038 |
| cost | $0.662 | **$0.572** | $0.596 |
| characters typed for `verify` commands | 1,525 | 290 | — |
| turns | 16 | 16 | 16 |
| test module executions | 10 | 10 | 20 |
| session wall time | 123 s | 144 s (API latency; test time 94 s in both) | 381 s |

With the plain form the Click-on cost falls to the Click-off level. Two
sessions are a direction, not a measurement of the same weight as the eight
above. A first attempt at this addendum was discarded: the plugin directory it
loaded was the worktree's `dist/claude`, which a branch switch replaced with
v1.0.1 while the sessions were running, so the parser rejected `verify --` mid
session and the model fell back to the JSON form.
