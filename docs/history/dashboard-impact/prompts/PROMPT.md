**좋아. 이번에는 “대시보드에 지표를 더 추가하는 것”이 아니라, “전체를 다시 돌리지 않은 차이가 첫 화면에서 바로 보이게 만드는 것”을 목표로 나누면 돼.**

확인한 공개 코드에는 이미 **회피한 실행시간 Hero, 전체 대비 부분 실행 그래프, 관리비용 상세 화면**이 있어. 따라서 아래 프롬프트는 기존 구현을 갈아엎지 않고, **전후 비교를 더 선명하게 만들고 → 묶음별 이유를 연결하고 → 그대로 공유할 수 있게 만드는 개선 작업**으로 구성했어.

**[Phase 0~5 개별 프롬프트 ZIP](sandbox:/mnt/data/click-dashboard-impact-prompts.zip)**
**[전체 프롬프트 통합 문서](sandbox:/mnt/data/click-dashboard-impact-all-prompts.md)**

Click 저장소를 연 코딩 에이전트에 **Phase 0부터 순서대로 입력**하면 돼. 각 단계는 결과와 검증 기록을 남기고 멈추도록 했고, 다음 단계는 그 기록을 읽고 이어서 작업하도록 구성했어.

## 최종적으로 만들 화면

아래 숫자는 **화면 구성 예시**야.

```text
이번 수정, 12개 중 3개만 다시 실행했습니다.

재사용으로 피한 테스트 재실행 시간
약 1분 30초 [추정]

전체 재실행 기준   ████████████████████  약 2분 [추정]
이번 실제 실행     █████                 30초 [실측]

3개 다시 실행 · 9개 결과 재사용
요청된 검증 묶음 12/12 결과 확보

동일 묶음·순차 실행 기준 / 과거 실행 기록 기반 추정
관리비용은 별도

[어떤 검증을 다시 실행하지 않았나요?]

──────────────────────────────────
최근 작업 흐름
묶음별 실행·재사용 이유

▸ 관리비용·요청시간·측정 조건
▸ 별도 실측 비교
```

**시간 자료가 부족하더라도 “12개 중 9개 재실행을 피했다”는 실제 동작은 크게 보여주는 것**이 중요해. 시간 추정치를 만들 수 없다는 이유로 첫 화면 전체가 “측정 정보 없음”으로 끝나지 않도록 하는 거야.

## Phase 0 — 현행 구현 감사와 변경 범위 확정

먼저 기존 구현을 확인해서 **이미 있는 기능을 다시 만드는 낭비**를 막는 단계야. 현재 projection은 실행 권한을 만들지 않는 읽기 전용 구조이므로, 이 경계도 그대로 유지하게 했어.

```text
Click 저장소의 대시보드를 ‘전체 재검증 대비 부분 재검증의 차이’가 즉시 보이는 화면으로 개선한다. 이번에는 Phase 0만 수행한다.

[최종 화면의 우선순위]
1. 재사용으로 피한 테스트 재실행 시간: 적합한 과거 실행 기록 기반 추정.
2. 전체 검증 묶음 중 실제로 다시 실행한 수와 재사용한 수.
3. 같은 묶음 전체 순차 실행 기준과 이번 실행의 시각적 비교.
4. 묶음별 재사용 이유와 최근 작업 흐름.
5. 관리비용·전체 요청시간·순시간 차이·초기 설정비용은 상세.
   다만 현재 표시 대상과 연결된 부정적 실측 결과를 숨기지 않는다.

[모든 Phase의 공통 규칙 — COMMON.md로 저장]
- 기존 구현을 먼저 확인하고 부족한 부분만 변경한다. 완료된 기능을 다시 만들지 않는다.

- 미측정은 null이다. 관찰된 0, 부분 기록, 비교 불가와 구분한다.
- 비교·공유·새로고침 때문에 테스트를 자동 실행하지 않는다.
- 토큰·요금 절감 수치를 시간이나 묶음 수에서 환산하지 않는다.
- 현재 기술 스택과 기존 내보내기 경로를 유지한다. 새 프레임워크·외부 서비스·분석 SDK를 도입하지 않는다.
- 사용자 변경과 다른 작업 폴더를 보존하고 git commit/push를 자동 수행하지 않는다.
- 각 Phase에서 변경에 관련된 검증을 실행한다. 변경 없는 전체 검증을 매번 반복하지 않는다.
- 기존 승인 절차를 우회하지 않는다. 권한·환경 부족은 명시하고 완료로 꾸미지 않는다.

[조사]

특히 revalidation_savings, outcomePresentation, renderOutcome,
readComparison, shareReport 또는 현재 대응 구현을 확인한다.

- METRICS.md: 기존 필드와 시간·횟수·부분 기록·비교 범위의 정의.

시간 비교와 Hero가 이미 있다면 ‘신규 구현’이 아니라 개선 항목으로 기록한다.
문서·코드·벤치마크 importer 버전이 다르면 실제 동작을 확인해 차이를 기록한다.

기존 기능을 보존하는 구체적인 변경 계획까지 작성하고 멈춘다.
```

## Phase 1 — 시간·횟수 지표와 단일 집계 경로 정리

현재 코드에도 **이번 실행시간 E + 재사용으로 생략한 비용 추정 A = 전체 순차 실행 예상 F**라는 집계가 있어. 이 산식을 다른 곳에 다시 만드는 대신, 화면과 내보내기가 같은 결과를 사용하도록 정리하는 단계야.

```text
Click 대시보드 개선 Phase 1을 수행한다.
docs/dashboard-impact/COMMON.md, PLAN.md, METRICS.md, progress.json을 읽는다.
Phase 0 결과와 현재 코드가 다르면 변경된 사실을 먼저 반영한다.

[목표]
화면·상세·JSON·독립 HTML이 동일한 집계 결과를 사용하게 한다.
기존 revalidation_savings와 projection을 우선 재사용한다.
프런트에서 같은 지표를 별도 산식으로 다시 구현하지 않는다.

[지표 계약]
N = 현재 요청의 전체 검증 묶음 수.
X = 실제 시작한 검증 묶음 수.
U = 실제 재사용이 적용된 검증 묶음 수.

정상 완료된 비교 가능 요청에서만 N = X + U를 사용한다.
진행·실패·취소·거부·미실행·미확정은 실제 상태대로 구분한다.
통과 수는 실행 수의 부분집합이므로 실행 수에 다시 더하지 않는다.

E = 이번 요청에서 실제 실행된 명령 구간의 시간 합계.
A = 실제 재사용된 묶음의 적합한 과거 성공 실행시간 합계.
F = E + A: 같은 묶음을 전부 순차 실행하는 경우의 환산 추정.
R = A / F: F > 0이고 비교 조건이 충족될 때만 계산하는 추정 비율.

횟수 비율 U / N과 시간 비율 R은 별개 지표다.

기존 필드의 의미를 유지한다.
- executed_test_execution_ms → E
- omitted_test_execution_ms → A
- full_sequential_test_execution_estimate_ms → F
- test_execution_reduction_ratio → R

현재 코드의 필드가 다르면 매핑을 문서화한다. 중복 스키마는 만들지 않는다.

[집계 조건]
- A의 시간 표본은 실제 적용된 재사용, 정확한 묶음·검사 정체성,
  원본 실행 출처와 적합한 계측 조건에 연결되어야 한다.
- 기존 표본 선택 규칙을 유지한다. 큰 절감치가 나오도록 표본을 고르지 않는다.
- F와 R은 정상 완료·완전한 범위·시간 근거·동일 순차 계측 조건이 확인될 때만 제공한다.
- 실행과 재사용의 계측 경계·Observer 조건을 대조한다.
  병렬 구간이나 비교 불가능한 조건을 순차 대기시간으로 변환하지 않는다.
- 일부 시간 표본만 있으면 A는 ‘시간 근거 있는 u/U개 묶음의 부분 추정’이다.
  F와 R은 null로 둔다.
  과거 표본 합계를 실제 절약시간의 하한인 ‘최소’나 ‘≥’로 표시하지 않는다.
- 재사용은 확정됐지만 시간 표본이 없으면 U는 유지하고 A는 null이다.
- 정상 완료된 전부 재사용은 E=0, 전부 실행은 A=0으로 표현할 수 있다.
  아직 실행하지 않은 요청의 E를 0으로 확정하지 않는다.
- parent와 children 중복, 별도 요청 혼합, 화면 갱신에 따른 중복 합산을 막는다.
- F는 Click 없는 원래 parent 명령의 실측시간도, 전체 요청 대기시간도 아니다.
- 전체 관리비용을 중첩된 시간 필드의 임의 차감으로 만들어내지 않는다.

[검증·완료]
정상 부분 재사용, 전부 실행, 전부 재사용, 0 분모,
일부/전체 시간 표본 누락, 계측 불일치, 실패·취소, 구형 데이터를 테스트한다.

기존 validator와 내보내기 호환성을 유지하고 필요할 때만 버전을 변경한다.
측정 모델만으로 실행·재사용 결정이 바뀌지 않는지도 확인한다.
METRICS.md, reports/phase-1.md, progress.json을 갱신하고 멈춘다.
```

## Phase 2 — 전후 차이가 보이는 첫 화면 개선

**여기가 가장 중요한 단계야.** 큰 숫자 하나만 보여주는 것이 아니라, **“전체는 이만큼인데 이번에는 이것만 실행했다”**가 눈에 들어오게 만드는 작업이야.

```text
Click 대시보드 개선 Phase 2를 수행한다.
docs/dashboard-impact/COMMON.md, PLAN.md, METRICS.md, progress.json과
Phase 1 결과를 읽고 현재 UI를 개선한다.

[목표]
첫 화면만 보고 ‘전부 다시 실행하지 않았다’를 이해할 수 있게 한다.
기존 Hero와 비교 그래프를 개선하며 동일한 화면을 중복 추가하지 않는다.

[첫 화면]
- 작업명·선택한 배치·시점·승인/실패 상태는 상단에 간결하게 유지한다.
- 대표 수치는 ‘재사용으로 피한 테스트 재실행 시간’과 ‘약 … [추정]’이다.
- 바로 아래에 ‘전체 N개 중 X개만 다시 실행 · U개 결과 재사용’을 크게 표시한다.
- 시간 근거가 부족하면 큰 제목을 ‘N개 중 U개 재실행을 피했습니다’로 바꾼다.
  부분 시간 추정과 근거 커버리지는 그 아래 표시한다.
- 정상 완료 시에만 ‘요청된 검증 묶음 N/N 결과 확보’를 표시한다.
  코드 전체의 정확성이나 테스트 충분성을 보장한다고 쓰지 않는다.

[두 가지 전후 비교]
1. 횟수 비교:
   ‘전체 재실행 기준 N개’ 대 ‘이번 실제 실행 X개 + 재사용 U개’.
   각 묶음을 대응되는 위치의 블록으로 표시하고 실행·재사용·미확정을 구분한다.
   이 기준선을 실제로 관찰한 이전 실행이라고 표현하지 않는다.

2. 시간 비교:
   ‘동일 묶음 전체 순차 실행 예상 F [추정]’ 대 ‘이번 실행 E [실측]’.
   두 막대는 같은 0 시작 시간 축을 사용한다.
   회피 추정 A가 어느 구간인지 직접 표시한다.
   F와 R이 null이면 시간 비율 그래프를 숨기되 횟수 비교는 유지한다.

‘동일 묶음·순차 실행 기준 / 과거 실행 기록 기반 추정 / 관리비용 별도’를
숫자 근처의 짧은 문구로 보여준다.
상세를 열어야만 추정임을 알 수 있게 하지 않는다.

‘75% 더 빠름’ 대신
‘테스트 명령 실행 구간 약 75% 감소 [추정]’처럼 범위를 적는다.
표시 예시 숫자는 fixture에서만 사용하고 운영 화면에는 하드코딩하지 않는다.

[상태별 화면]
첫 실행: ‘재사용할 기준 결과를 만드는 중’.
재사용 없음: ‘이번에는 N개 모두 다시 검증했습니다’와 실제 이유.
전부 재사용: 실행 0개를 표시하되 전체 요청이 0초였다고 표현하지 않는다.
진행·실패·취소: 상태를 우선 표시하고 완료된 사실만 유지한다.
재사용 예정·실행 전 중단을 성과로 표시하지 않는다.
새 작업에 현재 배치가 없으면 이전 작업의 성과를 현재 값으로 보여주지 않는다.

[표현·검증]
관리비용·요청시간·초기 설정·상세 계측은 아래 접힌 패널에 둔다.
색만으로 상태를 구분하지 말고 텍스트·아이콘/패턴을 함께 사용한다.
0 길이 막대를 임의의 양수 길이로 늘리지 않는다.
숫자는 막대 밖에서도 읽히게 한다.

모바일 390×844, 데스크톱 1440×900, 키보드 이동과 reduced-motion을 확인한다.
새로고침으로 수치가 중복 증가하거나 선택한 배치가 바뀌지 않게 한다.
관련 렌더링 테스트를 실행하고 reports/phase-2.md, progress.json을 갱신한다.
이번 Phase 완료 후 멈춘다.
```

## Phase 3 — 묶음별 이유와 작업 이력 연결

여기서는 **“9개 재사용했다고 하는데, 어떤 9개?”**라는 질문에 바로 답하게 만들어. 숫자를 클릭했을 때 실제 묶음과 이유가 연결되어야 해.

```text
Click 대시보드 개선 Phase 3을 수행한다.
docs/dashboard-impact/COMMON.md, PLAN.md, METRICS.md, progress.json과
Phase 2 결과를 읽는다.

[목표]
‘어떤 검증을 다시 실행하지 않았는지’와 ‘왜 가능한지’를 한 번의 선택으로 보여준다.
기존 묶음 목록·설명·배치 이력을 확장하며 별도 대시보드를 만들지 않는다.

[묶음별 비교]
각 묶음에 다음을 표시한다.
- 사용자에게 의미 있는 묶음명.
- 전체 재실행 기준에서는 실행 대상이라는 위치.
- 이번 실제 결과: 실행·재사용·진행·실패·중단·미실행·미확정.
- 실제 실행시간 또는 적합한 과거 실행시간 기반 회피 추정.
- 기존 canonical reason code에 근거한 한 문장 설명.

예:
‘관련 입력 변경 → 다시 실행’
‘기존 결과가 현재 조건과 일치 → 재사용’

정책 기반 재사용을
‘의존성을 자동 분석해 영향 없음을 증명’이라고 설명하지 않는다.
Shadow 예측·파일명 유사성·LLM 추측으로 실행 이유를 만들어내지 않는다.
샤딩되지 않은 검증 그룹을 억지로 샤드나 개별 테스트 케이스라고 부르지 않는다.

Hero와 비교 블록의 ‘재사용 U개’를 선택하면 해당 묶음 목록으로 연결한다.
각 항목의 상세에는 원본 실행 시점·출처·현재 재판정 방식·시간 근거를 연결한다.
로컬 상세와 공유본의 노출 범위는 기존 개인정보 보호 규칙을 따른다.

[작업 흐름]
이력을 ‘기준 실행 → 일부 수정 → 부분 재검증 → 다음 요청’으로 읽을 수 있게 한다.
실제 관찰한 변경 정보가 없으면 변경 파일이나 변경 의도를 추측하지 않는다.
과거 배치를 고르면 그 배치의 숫자·상태·근거를 보여준다.
현재 요청이 아닌 기록임을 배치명과 시점으로 명시한다.
완료되지 않은 새 작업에 이전 성공 결과를 자동 표시하지 않는다.

[누적 지표]
보관된 완료 요청에 대해
‘실제 재사용된 검증 묶음 요청 수’와
‘그 요청들에서 회피한 재실행 비용의 누적 추정’을 보조 지표로 제공한다.

같은 묶음의 별도 요청은 각각 집계하지만
같은 batch 재전송·polling은 중복 집계하지 않는다.

기간·시간대·보관 범위·누락 표본 수를 함께 표시한다.
일부 시간 근거만 있으면 ‘기록이 있는 요청의 부분 추정 합계’로 표시한다.
이 합계를 사람의 실제 대기 절감시간이나 평생 누적 절감이라고 표현하지 않는다.
실패·취소 이력은 숨기지 않되 정상 완료 성과 합계에는 섞지 않는다.

[검증·완료]
같은 요청 중복 수신, 별도 재시도, 세션/작업 변경, 과거 배치 선택,
부분 시간 근거, 이력 보관 제한, 권한 승계 없음과 근거 연결을 테스트한다.
reports/phase-3.md, progress.json을 갱신하고 멈춘다.
```

## Phase 4 — 별도 실측 비교와 공유 리포트 개선

**홍보에 직접 연결되는 단계야.** 대시보드에서 본 결과를 다시 설명하거나 편집하지 않고, 그대로 공유할 수 있게 만드는 거지.

기존 벤치마크는 비교 조건과 원시 시간을 기록하고, 기존 내보내기는 선택한 배치와 비교 자료를 공유하는 경로가 있으므로 이를 확장하도록 했어.

```text
Click 대시보드 개선 Phase 4를 수행한다.
docs/dashboard-impact/COMMON.md, PLAN.md, METRICS.md, progress.json과
Phase 3 결과를 읽는다.

[목표]
일상 추정 화면을 실측 비교와 구분하면서, 결과를 바로 공유할 수 있게 한다.
기존 benchmark driver·비교 importer·JSON·독립 HTML 경로를 우선 재사용한다.

[일상 기록과 별도 실측 분리]
- ‘이번 요청: 기록 기반 추정’과 ‘별도 비교: 직접 측정’을 명확히 분리한다.
- 실측 비교가 없다고 운영 중인 테스트를 추가 실행하지 않는다.
- 기존 명령 안내는 현재 driver 출력 형식과 importer가 실제로 호환되는지 확인한다.
- 실측 비교는 같은 최종 코드·테스트 범위·환경과 대응되는 반복 표본을 비교한다.
- ‘같은 샤드를 전부 실행’과 ‘원래 parent suite 전체 실행’의 기준을 분리한다.
- 명령 실행 구간 비교와 Hook/runner를 포함한 요청 구간 비교를 합산하지 않는다.
- fixture 결과는 fixture라고 표시한다.
  저장소 참조 자료가 첨부됐다고 fixture 결과가
  현재 사용자 저장소의 실측 결과가 되는 것은 아니다.
- 워밍업·초기 준비·추가 감사 비용·제외 표본·실패·음수 결과를 보존한다.
- 양의 절감률을 테스트 통과 조건으로 요구하지 않는다.

실측 차이 D = full_wall - click_wall로 유지한다.
D < 0이면 ‘이 비교에서는 Click 요청 구간이 더 길었습니다’라고 표시한다.
다른 fixture·시나리오의 음수 결과를 ‘이번 요청은 느려졌습니다’로 연결하지 않는다.
상세에 수치를 두되 비교 대상과 연결된 부정적 결과의 존재를 숨기지 않는다.

반복 통계에서는 ‘각 경로 중앙값’과 ‘쌍별 차이 중앙값’을 구분한다.
median(full)-median(click)이 median(full-click)과 같다고 가정하지 않는다.
최고 절감 표본만 자동으로 골라 대표 결과로 내보내지 않는다.

[공유 기능]
기존 export에 첫 화면의 전후 비교·묶음 수·짧은 설명을 그대로 반영한다.
공유용 요약 문구 복사 기능을 추가하거나 기존 기능을 개선한다.

예시 템플릿:
‘전체 {N}개 검증 묶음 중 {X}개만 다시 실행했습니다.
 {U}개 결과를 재사용했고, 피한 재실행 비용은 약 {A}입니다.
 과거 실행 기록 기반 추정·동일 묶음 순차 기준·관리비용 별도.’

시간 근거가 없으면 시간 문장을 제거한다.
실패·미완료를 성공 홍보문으로 만들지 않는다.

화면·복사 문구·JSON·HTML은 같은 숫자·상태·단위·반올림 규칙을 사용한다.
HTML은 외부 자산 없이 열리고,
경로·원시 명령·환경 값·토큰·계약 원문이 새지 않아야 한다.
새 필드와 묶음명도 공유 allowlist를 거친다.
사용자 문자열을 HTML로 실행하지 않는다.
공유 결과는 기록의 요약이지 발행자 인증이나 재사용 권한 증명이 아니다.

[토큰]
이번 범위에서 토큰 측정 엔진을 새로 만들지 않는다.
동일 비교 범위의 신뢰할 수 있는 실제 사용량 자료가 없으면 절감 수치를 표시하지 않는다.
실행시간·로그 글자 수·묶음 수를 토큰이나 요금으로 환산하지 않는다.
캐시 출력 재전달을 자동적인 토큰 절감으로 계산하지 않는다.

관련 importer·export·악성 입력 테스트를 실행한다.
reports/phase-4.md, progress.json을 갱신하고 멈춘다.
```

## Phase 5 — 실제 흐름 검증과 화면·문서 통합 감사

마지막은 **예쁜 화면만 만들어진 상태가 아니라, 실제 실행 결과와 화면이 맞는지** 확인하는 단계야.

```text
Click 대시보드 개선 Phase 5를 수행한다.
docs/dashboard-impact/COMMON.md, PLAN.md, METRICS.md, progress.json과
Phase 0~4 보고서를 읽고 통합 검증 및 문서 정리를 수행한다.

[실행 검증]
기존 지원 환경과 Hook/runner fixture를 사용하여 다음 흐름을 실제로 확인한다.
기준 실행 → 일부 변경 → 적법한 재판정 → 일부 실행/일부 재사용 → 화면 및 내보내기.

실제 권한 경로를 통과시킨다.
통과 receipt·재사용 결정·성과 수치를 주입하지 않는다.
합성 데이터는 렌더링/산식 단위 테스트에만 쓰고 E2E 실측과 구분한다.
지원되지 않는 환경에서 권한 검사를 완화해 성공한 것처럼 만들지 않는다.

[필수 회귀 시나리오]
1. 정상 부분 재사용:
   N/X/U 및 A/E/F/R이 원본 기록과 일치.

2. 전부 실행:
   A=0, 실행량 감소 없음. 낭비 제거 성과를 꾸미지 않음.

3. 전부 재사용:
   E=0. 요청 전체 시간 0 또는 토큰 100% 절감으로 표현하지 않음.

4. 일부 시간 표본 누락:
   횟수는 표시, 부분 추정은 명시, F/R은 null.

5. 시간 표본 전부 없음:
   재사용 횟수는 유지, 시간은 미측정.

6. 진행·실패·취소·미확정·실행 전 거부:
   상태 유지, 미실행을 재사용에 합산하지 않음.

7. 재사용 예정만 존재:
   실제 재사용 성과에 포함하지 않음.

8. 중복 이벤트·새로고침:
   누적치 불변. 실제 새 요청은 별도 집계.

9. 새 계약/작업에 배치 없음:
   이전 성과를 현재 작업에 대입하지 않음.

10. 오래된 데이터·0 분모·다른 계측 조건·병렬 기록:
    거짓 시간/비율을 생성하지 않음.

11. 실측에서 순시간 증가:
    음수 유지, 정확한 fixture/시나리오에만 연결.

12. 같은 입력의 화면·복사·JSON·HTML:
    숫자·단위·범위·상태·추정 표시 일치.

13. 악성 라벨/HTML·비정상 JSON·다른 세션 기록:
    실행·정보 노출·범위 혼합 없음.

14. 신뢰할 토큰 자료 없음:
    허구의 토큰·요금 절감 수치 없음.

[화면 검수]
브라우저 실행이 가능하면 실제 렌더링으로 다음을 점검하고 캡처한다.
- 1440×900:
  첫 화면에서 피한 시간, 실제 실행/재사용 수, 전후 차이를 읽을 수 있는가?
- 390×844:
  핵심 수치·추정 표시·상태가 잘리거나 과밀하지 않은가?
- 시간 자료가 없어도 ‘무엇을 다시 실행하지 않았는가’를 이해할 수 있는가?
- 실패·진행 상태를 성공 성과로 착각할 수 없는가?
- 상세를 열면 관리비용·측정 범위·재사용 근거를 찾을 수 있는가?
- 색을 구분하지 못해도 상태를 읽고 키보드로 탐색할 수 있는가?

브라우저나 런타임이 없으면 미실행 항목과 이유를 보고하고 통과로 표시하지 않는다.

[문서·최종 산출물]
README 및 VERIFICATION_EFFICIENCY.md의 화면·필드·비교 안내를 실제 구현과 맞춘다.
문서 예시·합성 fixture·실제 측정 결과를 분리한다.

현재 구현의 성공 기준은 숫자를 크게 만드는 것이 아니라,
전체 재검증 대신 부분 재검증한 사실과 비용 차이를 명확히 전달하는 것이다.

reports/final.md에 변경 파일, 검증 명령/결과, 실행하지 못한 항목,
호환성·보안 확인, 화면 캡처 위치, 남은 제한을 기록한다.

progress.json은 실제 완료된 단계만 completed로 표시한다.
실측 성능 향상이 없거나 지원 환경이 부족하면 그 결과도 그대로 남긴다.
마지막으로 필요한 통합 회귀를 수행하고, 변경 없는 전체 테스트 반복은 피한다.
코드 commit/push는 수행하지 않는다.
```

**Phase 2까지 완료하면 첫 화면의 전후 차이가 살아나고, Phase 4까지 완료하면 그 화면을 홍보 자료로 바로 공유할 수 있게 되는 구성**이야.

이번 개선의 중심 문장은 이것으로 고정하면 돼.

> **“전체를 다시 돌리는 대신, 이번에는 이것만 다시 확인했습니다.”**

그 문장 바로 옆에 **실제로 다시 실행한 묶음, 재사용한 묶음, 피한 실행 비용의 추정치**가 보이게 만드는 게 핵심이야.
